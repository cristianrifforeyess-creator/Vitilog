El conjunto, en un minuto

VITILOG es una aplicación web hecha con HTML, CSS y JavaScript puro, más SQL para la base de datos. No usa ninguna librería externa.

Son 13 páginas HTML que comparten 5 archivos JavaScript y 1 archivo CSS. Cada página es una pantalla distinta, pero todas cargan los mismos cinco archivos y se apoyan en ellos.

          ┌──────────────────────────────┐
          │   Cualquier página HTML      │
          │   (inicio, mapa, admin...)   │
          └──────────────┬───────────────┘
                         │ usa
        ┌────────────────┴────────────────┐
        ▼                                 ▼
  ┌───────────┐                    ┌────────────┐
  │ shell.js  │  ← el esqueleto    │ styles.css │
  │ menú,mapa │                    │  el diseño │
  └─────┬─────┘                    └────────────┘
        │ pide datos a
        ▼
  ┌───────────┐
  │ store.js  │  ← la memoria
  │  guarda   │
  └─────┬─────┘

        ├────────────────┬──────────────────┐
        ▼                ▼                  ▼

  (el navegador)   el mensajero      la base compartida

  config.js  →  decide TODO lo anterior (modo local o nube)
  data.js    →  los datos fijos: comunas, plantas, coordenadas
La idea que hay que entender

Cada archivo tiene un solo trabajo. store.js guarda datos pero no sabe dibujar; shell.js dibuja pero no sabe guardar. Eso se llama separación de responsabilidades, y es lo que permite cambiar una parte sin romper el resto.

js/config.jsEl interruptor

84 líneas, todas constantes. No hace nada por sí mismo: solo guarda valores que cambian el comportamiento del sitio.

const MODO_DATOS  = 'auto';    // dónde guardar: navegador o nube
const MODO_MAPA   = 'propio';  // qué mapa dibujar
const SUPABASE_URL = '';      // si está vacío → modo local

Si mañana quieres conectar la base compartida, solo escribes la dirección aquí. No se toca ningún otro archivo.

Lo esencial

Toda la configuración vive en un solo lugar. Nada de valores sueltos repartidos por el código.

js/nube.jsEl mensajero

84 líneas. Su único trabajo es hablar con la base de datos por internet. Usa fetch, que viene incluido en el navegador — por eso no hace falta ninguna librería.

Ofrece cuatro operaciones, que son las cuatro cosas que se pueden hacer con datos:

Nube.listar('cargas')              // leer
Nube.guardar('cargas', fila)       // crear o actualizar
Nube.actualizar('cargas', ...)     // modificar
Nube.borrar('cargas', filtro)     // eliminar

Eso se llama CRUD: Crear, Leer, Actualizar y Borrar. Y como se comunica por direcciones web con métodos estándar, se dice que consume una API REST.

Lo esencial

No sabe qué es una “carga” ni una “cuenta”. Solo sabe enviar y recibir. Si mañana cambiaras Supabase por otra base, este es el único archivo que tocarías.

js/data.jsLa libreta

156 líneas. Guarda toda la información fija del proyecto dentro de un objeto llamado DATA: las 11 comunas, las 10 plantas, las rutas de ejemplo y el marco del mapa.

const DATA = {
  comunas: [ { nombre: 'Curicó', lat: -34.98, lng: -71.24 }, ... ],
  puntos:  [ { nombre: 'EnerVid SpA', tipo: 'Biomasa', ... }, ... ],
  ...
};

Además tiene una función importante, proyectar(), que convierte coordenadas del mundo real en una posición dentro del mapa dibujado:

function proyectar(lat, lng) {
  // regla de tres: de grados geográficos a puntos del dibujo
  return { x: ..., y: ... };
}
Lo esencial

Las plantas solo guardan latitud y longitud. Su posición en pantalla se calcula, no se escribe a mano. Por eso, al agregar una planta nueva, aparece sola en su lugar correcto.

js/store.jsLa memoria

368 líneas. Es la base de datos de la aplicación. Guarda las cuentas, las cargas publicadas y las plantas, y maneja el inicio de sesión.

Su idea central: la caché

Al abrir cualquier página, lee todos los datos una sola vez y los deja en memoria. Desde ahí responde al instante, sin volver a pedir nada.

_cache: { cuentas: [], cargas: [], puntos: [] }

Guarda en dos lugares posibles

Este patrón se repite en cada función que guarda algo:

// 1. actualiza la memoria
lista.push(cuenta);

// 2. decide dónde dejarlo de verdad
if (this.enNube()) await Nube.guardar('cuentas', cuenta);
else this._write(this.K_ACCOUNTS, lista);

Las contraseñas no se guardan

Se guarda su huella: un código de 64 caracteres calculado con SHA-256, imposible de revertir. Al iniciar sesión se calcula la huella de lo que la persona escribió y se compara.

const buf = await crypto.subtle.digest('SHA-256', sal + clave);

La sal es un texto aleatorio distinto por cuenta que se suma antes de cifrar. Sirve para que dos personas con la misma contraseña tengan huellas distintas.

Lo esencial

El resto del sitio pide datos a Store sin saber ni preguntar dónde están. Esa indiferencia es lo que permite cambiar de navegador a nube sin tocar las 13 páginas.

js/shell.jsEl esqueleto

552 líneas, el archivo más grande. Contiene todo lo que se repetiría en las 13 páginas, escrito una sola vez: el menú, el mapa, las ventanas emergentes y los cálculos de distancia.

Lo más importante: init()

Toda página protegida empieza con esta línea, que hace cuatro cosas de una vez:

Shell.init('cargas', { rol: Store.ROL_EMPRESA }).then(listo => {
  if (!listo) return;
  // ... aquí recién empieza el contenido de la página
});
  1. Carga los datos y espera a que estén listos
  2. Si no hay sesión iniciada, devuelve al login
  3. Si la cuenta es de otro rol, la manda a su página
  4. Dibuja el menú que corresponde a ese rol

Así un viñatero no puede entrar a la página de las empresas aunque escriba la dirección a mano.

El mapa

Está dibujado en SVG (gráficos vectoriales) sobre coordenadas reales: la costa, las dos cordilleras y la Ruta 5 en su posición geográfica. Cada marcador se ubica llamando a proyectar().

Las distancias

Se calculan con la fórmula de Haversine, que da la distancia real en kilómetros entre dos coordenadas sobre la superficie curva de la Tierra.

Lo esencial

Si el menú, el mapa o los avisos estuvieran copiados en cada página, cualquier cambio habría que hacerlo 13 veces. Al estar aquí, se hace una sola vez.

13 archivos .htmlLas pantallas

Todas siguen exactamente la misma forma, así que entendiendo una entiendes las trece:

  1. El HTML define solo la estructura: los recuadros vacíos, los campos, los botones.
  2. Se cargan los 5 archivos JS, siempre en el mismo orden.
  3. Un bloque de código propio llena esa estructura con datos reales.
<!-- 1. la estructura, vacía -->
<select id="comuna"></select>
<button onclick="publicar()">Publicar carga</button>

<!-- 2. los archivos compartidos -->
<script src="js/store.js"></script>
<script src="js/shell.js"></script>

<!-- 3. el código de esta página -->
<script>
  Shell.init(...).then(listo => {
    // llenar el select con las comunas de DATA
    // validar el formulario
    // llamar a Store.addCarga()
  });
</script>
Lo esencial

El HTML nunca trae datos escritos a mano. Siempre llega vacío y lo llena JavaScript. Por eso el mismo inicio.html se ve distinto para cada usuario.

css/styles.cssEl diseño

431 líneas para las 13 páginas. Lo que lo hace manejable es que los colores están en variables, no escritos en cada regla.

:root { --surface: #FFFFFF; --text-primary: #1D2B1F; }

html[data-theme="dark"] { --surface: #1B221A; --text-primary: #ECF1EC; }

.card { background: var(--surface); }   /* usa la variable */

Por eso el modo oscuro es una sola línea de JavaScript: al cambiar data-theme, se redefinen todas las variables de golpe y cada componente se actualiza solo.

Y con @media el diseño se adapta al celular: bajo 760 píxeles el menú lateral se esconde y aparece uno abajo, como en una app.

Lo esencial

Ningún componente conoce un color. Solo conoce el nombre de un color. Cambiar el tema es cambiar qué significan esos nombres.

sql/esquema.sqlLas tablas

125 líneas. Es el único archivo que no corre en el navegador: se ejecuta una vez en el servidor de base de datos para crear las tres tablas.

create table cuentas (
  email       text primary key,        -- no se repite
  rol         text check (rol in ('vinatero','empresa','admin')),
  clave_hash  text not null,           -- obligatorio
  activa      boolean default true
);

Las tres tablas son cuentas, cargas y puntos. Y están relacionadas: cada carga apunta a la cuenta que la publicó.

owner_email text references cuentas(email) on delete cascade

Eso es una llave foránea: obliga a que toda carga pertenezca a una cuenta que existe. Y si se borra la cuenta, sus cargas se borran con ella.

Lo esencial

La base también valida. Aunque alguien se saltara el formulario, no podría guardar un volumen negativo ni un rol inventado.

Las tres frases que valen por toda la guía

  1. Cada archivo tiene un solo trabajo. Por eso se puede cambiar uno sin romper los demás.
  2. El HTML llega vacío y JavaScript lo llena. Ningún dato está escrito a mano en la pantalla.
  3. Los datos se leen una vez y quedan en memoria. Por eso el sitio responde al instante.
